# CLAUDE.md — Memória Reflexiva

Memória operacional deste projeto para o Claude Code. Curto e prático — para o detalhe completo,
siga os links.

## Missão

App pessoal de IA que transforma um acervo (livros, cartas, reflexões, documentos) em memória
inteligente e pesquisável, usada para apoiar novas reflexões. `Biblioteca → memória rastreável →
perfil autoral com evidências → reflexão assistida → revisão humana`. **Sempre consulte
`docs/specs/` antes de projetar ou construir um módulo** — é a especificação funcional canônica
fornecida pelo dono do produto. Comece por `docs/specs/MR-ARQ-arquitetura-tecnica-mestra.md`.

## Stack (verificada, não assumida)

TanStack Start + React 19 + Vite 8 + Tailwind 4 + shadcn/ui, scaffold do Lovable, bun como
gerenciador de pacotes. Backend: **Lovable Cloud** (integração nativa `enable_database`,
`stack: "supabase"`). Roteamento por arquivo em `src/routes/` (ver `src/routes/README.md` — não
criar `src/pages/` nem convenções de Next.js/Remix).

**Importante sobre o Lovable Cloud**: o projeto Supabase por trás dele é gerenciado pelo Lovable e
**não tem uma referência estável e visível de fora** — o Lovable já reatribuiu o backend gerenciado
para um projeto diferente uma vez nesta sessão (ver `docs/DECISIONS.md`, 11/09/2026). Nunca hardcode
ou documente um `project_id`/ref específico como se fosse permanente. Ver "Como aplicar migrations"
abaixo.

## Comandos

```bash
bun install        # instalar dependências (lockfile: bun.lock)
bun run dev         # servidor de desenvolvimento
bun run build        # build de produção
bun run lint          # eslint
bun run format         # prettier --write
```

### Como aplicar migrations (Lovable Cloud)

O projeto Supabase por trás do Lovable Cloud não é diretamente endereçável por fora (sem `project_id`
estável, sem chave de serviço exposta). O fluxo que funciona:

1. Escrever/atualizar a migration em `supabase/migrations/` normalmente — **isso continua sendo a
   fonte de verdade do schema**, commitada no GitHub.
2. Pedir ao próprio agente do Lovable (`mcp__Lovable__send_message`) para aplicar exatamente esse
   SQL ao backend que ele tem conectado no momento — ele tem acesso direto (ferramenta
   `supabase--migration` do lado dele) que nós não temos.
3. O Lovable pode precisar acrescentar `GRANT`s (seu Postgres gerenciado não dá os privilégios
   default que um projeto Supabase criado manualmente teria) — pedir que ele informe o SQL exato
   dos `GRANT`s usados, e commitar essa diferença de volta em `supabase/migrations/` para manter o
   GitHub fiel ao que está realmente em produção.
4. Depois de qualquer mudança de schema, rodar `bun run typecheck`/`lint`/`build` — o Lovable
   regenera `src/integrations/supabase/types.ts` automaticamente e isso pode introduzir problemas
   de formatação (rodar `bun run format`).

Se algum dia o projeto migrar para a integração "Supabase" separada (conectar um projeto Supabase
externo, ao invés do Lovable Cloud), aí sim existe um `project_id` estável e dá para usar
`mcp__Supabase__apply_migration`/`execute_sql` diretamente como foi feito na Fase 0 original — ver
`docs/DECISIONS.md` para o histórico completo.

## Arquivos gerados pelo Lovable — não editar à mão

`src/integrations/supabase/types.ts`, `client.server.ts` e `auth-middleware.ts` têm o cabeçalho
"This file is automatically generated. Do not edit it directly." — são scaffolding do Lovable Cloud
(cliente admin com `service_role`, middleware de validação de Bearer token em server functions).
Se precisar mudar o comportamento deles, peça ao agente do Lovable ou ajuste via migration/schema;
não edite o arquivo gerado diretamente, ele será sobrescrito.

## Regras de banco (não negociáveis)

- Depois da fundação, **toda** alteração estrutural do Supabase é uma migration em
  `supabase/migrations/`, aplicada e commitada — nunca só no Dashboard.
- Toda tabela pessoal tem `owner_id` (ou `id` referenciando `auth.users.id`) e **RLS ativo** desde a
  migration que a cria. Rodar o advisor de segurança do Supabase depois de qualquer DDL.
- Nunca misturar embeddings de modelos/versões diferentes na mesma busca.
- Ver `docs/DATA_MODEL.md` para o modelo completo planejado e `docs/SECURITY.md` para as regras de
  segurança.

## Regra de não contaminação (crítica)

Texto gerado pela IA nunca é memória autoral automaticamente. Só entra após revisão humana +
aprovação explícita + ação explícita de incorporar. Conteúdo `authorship_type = external` nunca
alimenta o perfil autoral como evidência de estilo.

## Responsabilidades por ferramenta

Lovable → UX/UI. GitHub → fonte do código e das migrations. Supabase → backend e dados. Claude Code
→ engenharia e implementação. Nunca criar estrutura de banco concorrente entre Lovable e Claude
Code — ver `docs/ARCHITECTURE.md`.

## Segurança operacional

- Nunca commitar `.env`/`.env.local` (só `.env.example`, com nomes de variáveis).
- Segredos de IA/backend só como variáveis de ambiente de servidor — nunca `VITE_*`.
- Operações destrutivas (drop table, reset de banco, limpar Storage, force push, apagar branch
  compartilhada) exigem confirmação explícita do dono do produto antes de executar.
- Nunca `git push --force` ou `--no-verify` sem autorização explícita.

## Definição de pronto

Uma funcionalidade só está concluída quando: comportamento principal funciona + persistência
funciona + RLS protege + loading existe + empty state existe + erro é tratado + tipos corretos +
testes relevantes passam + build passa + documentação (`docs/PROJECT_STATE.md` e o que mais se
aplicar) está atualizada. "Renderiza na tela" não é "concluído".
